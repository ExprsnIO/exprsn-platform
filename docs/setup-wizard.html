Setup Wizard & First Run

The platform ships an interactive setup wizard — npm run setup — that configures the entire environment surface of the unified process, section by section, into a grouped, commented .env. It replaces hand-editing .env.example as the recommended first-run configuration step (the manual cp .env.example .env path remains the non-interactive fallback).

Command
npm run setup (landed as TASK-045)
Script
scripts/setup-tui.js
Dependencies
None — pure Node (readline + ANSI escapes), no external packages
Optional argument
Path to the env file to edit: node scripts/setup-tui.js path/to/x.env (default ./.env)
Requires
An interactive terminal (TTY); the script exits with an error otherwise
Source of truth
The wizard's field schema tracks src/config/index.js and .env.example

First-run flow

The wizard sits between certificate generation and database bootstrap:

npm install            # also resolves @exprsn/shared via file:./shared
npm run gen:certs      # dev self-signed cert (required for the HTTPS edge)
npm run setup          # interactive wizard — writes ./.env
npm run db:bootstrap   # create db `exprsn` + one Postgres schema per module
npm run db:migrate     # sync each module's models into its schema
npm start              # https://localhost:8443 — verify: curl -k https://localhost:8443/health

Non-interactive fallback: cp .env.example .env and edit by hand. Postgres and Redis must be up (see npm run infra:up) before db:bootstrap and npm start.

How it treats your .env

  • Loads the existing file if present, otherwise seeds from .env.example. The main menu header shows which one was loaded.
  • Nothing is written until you choose "Review & write .env". Browsing and editing values is entirely in-memory; quitting with unsaved changes prompts for confirmation.
  • An existing file is backed up first to .env.bak-<timestamp> before being overwritten.
  • Keys it does not manage are preserved verbatim — anything in your .env outside the wizard's schema is carried into the output under an "Unmanaged keys" section.
  • The written file is grouped into commented sections mirroring the wizard's menu; unset optional keys are emitted as comments (# KEY=) so the full surface stays discoverable.

Secrets

Secret values are always masked in the UI (shown as ••••••••). Fields with a ⚡ Generate option mint a cryptographically random hex secret at a documented strength:

SecretGenerated strength
SERVICE_TOKEN_SECRET48 bytes (96 hex chars)
JWT_SECRET32 bytes
SESSION_SECRET32 bytes
DEV_BYPASS_SECRET32 bytes

Other generator-equipped secrets (webhook secrets, METRICS_TOKEN, ATPROTO_USER_DID_SECRET) also use 32-byte hex. See the Secrets & Rotation runbook for what each secret protects and how to rotate it.

Validation

Invalid values are rejected at entry time, and the review screen re-checks everything before writing:

  • Ports must be integers 0–65535; numeric fields must be numbers; sample rates must be fractions 0..1; risk thresholds must be 0–100.
  • Secret minimums: SERVICE_TOKEN_SECRET, JWT_SECRET, SESSION_SECRET, and DEV_BYPASS_SECRET must be ≥ 32 characters. SERVICE_TOKEN_SECRET is required — its absence is flagged as a problem.
  • Enum-only fields are picked from a menu, never typed:
    VariableAllowed values
    CORTEX_MODERATION_MODEoff | shadow | enforce
    FILEVAULT_IMAGE_MODERATIONoff | shadow | enforce
    FILEVAULT_VIDEO_MODERATIONoff | shadow | enforce
    LIVE_RECORDING_MODERATIONoff | shadow | enforce
    ATPROTO_DID_METHODexprsn | web | plc
    DEFAULT_AI_PROVIDERclaude | openai | cortex
  • CORTEX_ASYNC_ROLE must never appear in .env — the wizard errors if it finds it there, because the gateway refuses to boot with it set. Only the worker:* npm aliases set it, per-process.
  • DEV_BYPASS=true under NODE_ENV=production is flagged: the bypass is fail-closed, so the setting is inert and should be removed.
  • Placeholder secrets (change_me etc.) are listed as problems. You can still choose "Write anyway" — the wizard warns, it doesn't block.

Dev quick-start preset

The ⚡ Dev quick-start menu entry fills every untouched field with its local-development default, sets NODE_ENV=development, and generates fresh secrets wherever placeholder values remain (SERVICE_TOKEN_SECRET, JWT_SECRET, SESSION_SECRET, plus random passwords for Postgres/RabbitMQ/LDAP/Kerberos placeholders). One selection, then review and write.

Derived service URLs

The 13 *_SERVICE_URL variables (CA_SERVICE_URL, AUTH_SERVICE_URL, SPARK_SERVICE_URL, …, plus CA_URL/CA_BASE_URL aliases and HERALD_SERVICE_URL) are not hand-editable in the wizard. In the unified platform they must all point back at the single origin, so they are derived from PUBLIC_HOST and TLS_ENABLED as <scheme>://<host>/<module-prefix> and written into their own commented block of the output file.

Review & write

The review screen shows, before anything touches disk:

  • A feature summary — which optional subsystems the config enables (AT-Proto bridge, plugins, low-code, cortex and its moderation/vision/python/Ollama options, FileVault image/video moderation, live recording moderation, metrics, Sentry, RabbitMQ).
  • The worker processes this config requires: always worker:timeline and worker:prefetch; conditionally worker:atproto, worker:cortex, worker:filevault-moderation, worker:video-moderation, and worker:live-recording-moderation depending on the flags you enabled.
  • Any outstanding problems (see Validation above), with the choice to write anyway.
  • A Preview file option that renders the exact .env that would be written.
