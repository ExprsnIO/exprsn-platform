Overview

Exprsn-Cortex is the platform's local-LLM engine: an agent tool-calling loop, a guardrail engine (deterministic rules plus an LLM judge, with a test-gated lifecycle), custom tool and skill registries, long-running agent tasks, and guarded customer-service chat/email flows with human-review escalations. All inference runs on an external OpenAI-compatible llama.cpp router (CORTEX_LLM_BASE_URL, default http://127.0.0.1:8080/v1) — no cloud APIs.

As a platform module it exports { name, app, init } — JSON API only, no views, no listen(). It owns the cortex Postgres schema, attaches no Socket.IO namespace, and pushes long-running work onto a Bull queue drained by a separate worker. It is the newest of the four post-consolidation additions and, like plugins and lowcode, ships behind its own feature flag.

Cortex is also an in-process LLM source for the rest of the platform: services/cortex/src/client.js is the single supported façade other modules use to reach the local model (see Integration).

Request routing & the inference/flow split

Interactive routes and queued tasks run through the flow layer (engine/jobs.js), which applies guardrails and — when CORTEX_MODERATE is on — the fail-open moderator screen. The in-process client.js façade binds only to the inference layer (engine/agent.js), never the flow layer, so a moderator → cortex → moderator cycle is structurally impossible (ADR 0001). The CORTEX_ENABLED gate is checked before any inference and fails closed.

The CORTEX_ENABLED gate

The module always mounts, but is dark by default. Its behavior is governed entirely by CORTEX_ENABLED (default false):

StateBehavior
CORTEX_ENABLED=false (default)init() logs "Cortex module loaded INERT" and returns immediately — no DB authenticate, no cache/queue init, no data-dir creation. /cortex/health still answers; every /cortex/api/v1 route returns 503 {error:'CORTEX_DISABLED'} via the requireEnabled middleware.
CORTEX_ENABLED=trueFull init: DB authenticate, cache + queue setup, data directory creation. In development, sequelize.sync({ alter: true }) runs. Routes enforce their per-route CA-token + admin checks.
The flag is also re-checked inside the in-process client façade before the lazy require of the inference engine, and it fails closed — calling the engine while cortex is dark is refused with CortexDisabledError (503), not silently allowed through to the router.

Registries: guardrails, tools, skills

Guardrails, custom tools, and skills share a common registry router shape (list, LLM-build a spec from a description, save, get, delete, and a :verb action). Guardrails and tools are test-gated — enabling one requires its bundled test suite to pass; skills are not. All reads require read; all mutations require write + admin.

Data models

Registry entities (guardrails, skills, tools) use UUID primary keys; run artifacts (tasks, sessions, outbox, reviews) keep the engine's human-readable string ids (e.g. task-…, rev-…). Background jobs & concurrency

Cortex splits work between the gateway process and a separate worker:

WhereWhat runs there
In-process (gateway)All interactive flows — assistant chat, CS chat/email, guardrail/tool/skill build+test+run, the LLM judge, one-shot completions. Serialized behind an LLM concurrency semaphore in src/lib/llama.js: two separate pools, text (max CORTEX_LLM_CONCURRENCY, default 2) and vision (max CORTEX_VISION_CONCURRENCY, default 1), so async image work never starves interactive chat.
Bull queue cortex-tasks (worker)Only long-running agent runTask executions (from POST /tasks). Run via npm run worker:cortex. Jobs use attempts: 1 — an agent task is not idempotent, so it is never auto-retried. The worker drains queued jobs even if the flag is later turned off (it warns but keeps processing).

Integration: the in-process client & moderator

services/cortex/src/client.js is cortex's public in-process façade — the only supported way another module reaches the local LLM. Consumers require it relatively; it is deliberately not part of @exprsn/shared (which stays a dependency-leaf, since cortex depends on shared). Its surface: isEnabled, complete(), judge(), health(), and the vision helpers moderateImage()/describeImage()/moderateFrames()/describeFrames()/visionAvailable(), plus the error classes CortexDisabledError (503) and CortexUnavailableError (503).

Two ADR 0001 invariants keep it safe:

  • The façade binds only to cortex's inference layer (engine/agent.js), never its flow layer (engine/jobs.js). Because the cortex→moderator call (moderatorScreen()) lives only in jobs.js, a moderator → cortex → moderator cycle is structurally impossible. engine/agent.js pulls in no Sequelize models, no Bull, and opens no DB/Redis connection at require time.
  • The CORTEX_ENABLED gate is evaluated before the lazy require and fails closed.

Callers own their failure policy, because the right one differs by consumer:

ConsumerOn LLM failureWhy
moderator (ai-providers/cortex.js)fail CLOSED — throw, so the provider factory falls back to a cloud providerthe provider is the verdict; a synthetic "safe" score would ship unmoderated content
lowcode (cortex flow action, AI fields)fail SOFT — record { error } / keep the prior valuean LLM hiccup must not block a record write
filevault worker (image/video moderation)governed by FILEVAULT_IMAGE_MODERATION — escalate-onlycalls the façade directly, bypassing the provider factory; a wrong verdict can only add a review item

Cortex ↔ moderator (the flow layer). With CORTEX_MODERATE=true, cortex additionally screens chat/CS content through POST /moderator/api/moderate/content (service-HMAC headers, fail-open). The strongest verdict wins (pass<warn<escalate<block). A request tagged sourceService:'cortex' never selects the cortex provider (loop guard). Note this is separate from moderator's own CORTEX_MODERATION_MODE (governs whether moderator uses cortex to score text) and from FILEVAULT_IMAGE_MODERATION (governs image verdicts) — neither of those keys is read inside services/cortex/.

Security posture

Every /cortex/api/v1 route requires a valid CA bearer token; registry mutations (guardrails, tools, skills), the review queue, and the prompt log are additionally platform-admin gated. The two highest-risk surfaces are separately flag-gated and off by default:

  • Python custom-tool execution (CORTEX_PYTHON_TOOLS_ENABLED) — arbitrary code execution; runs under CPU/memory/file-size/wall-clock limits and a restricted read-path seatbelt profile, but needs real sandboxing before production use.
  • Private-network HTTP tool targets (CORTEX_TOOL_ALLOW_PRIVATE_HOSTS) — an SSRF guard; private hosts are refused unless explicitly allowed.

Inference is local-only (no cloud APIs leave the host), guardrails are enforced on both input and output paths, and the moderator layering call is fail-open so an LLM outage degrades to the local guardrail verdict rather than blocking traffic. The platform-wide fail-closed dev auth bypass (DEV_BYPASS) applies here as elsewhere and must never be weakened.
