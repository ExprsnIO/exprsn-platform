## Plugin model & lifecycle

### Execution kinds in MVP  —  _decided_

**Question:** Which plugin execution kinds ship in the MVP?

**Choice:** declarative + webhook

**Rationale:** Untrusted code stays out-of-process; internal is deferred to a post-MVP first-party-only tier.

Options considered:
- **declarative + webhook** ✅ — Trusted data evaluated by our engines, plus signed webhooks to out-of-process plugins. No foreign code in the gateway.
- **declarative only** — Smallest surface: condition trees / workflow specs only. No external plugins yet.
- **declarative + webhook + internal** — Also allow in-process first-party code at MVP. Higher blast-radius risk on a single-instance gateway.

### Plugin loading model  —  _decided_

**Question:** How are plugins discovered, loaded and isolated?

**Choice:** manifest-registry + hook-bus

**Rationale:** Single-instance gateway has no in-process sandbox (vm2 dead); foreign require() risks all ten modules.

Options considered:
- **manifest-registry + hook-bus** ✅ — Plugins are data (a manifest row); a plugins module + in-process hook bus dispatches events. Scoped, disable-without-restart.
- **dynamic require (npm-style)** — Discover exprsn-plugin-* packages and require() them into MODULES. Max power, no trust boundary, breaks fail-fast boot.
- **hybrid (registry now, require later)** — Manifest-registry for MVP; reuse dynamic-require mechanics only for signed in-repo code post-MVP.

### What are the first plugins?  —  _open_

**Question:** Should the first plugins refactor moderator, or be net-new?

**Choice:** _undecided_

Options considered:
- **refactor moderator rules/agents** ⭐ — Re-express existing moderator rules/agents on the framework first — proves the model, removes duplication.
- **net-new plugins alongside moderator** — Leave moderator as-is; build fresh example plugins. Faster to a demo, but two parallel extensibility systems.
- **both, refactor first** — Refactor one moderator rule as the proof (Phase 1.5), then add net-new plugins.

### Frontend surfaces in MVP  —  _open_

**Question:** Do plugins contribute SPA surfaces in the MVP?

**Choice:** _undecided_

Options considered:
- **declarative surfaces feed** ⭐ — Manifest declares surfaces; SPA fetches GET /plugins/api/surfaces and renders known types. No plugin JS shipped.
- **defer to post-MVP** — Backend-only for MVP; SPA contributions land in Phase 3+.
- **never (backend-only plugins)** — Plugins are purely server-side; frontend is always first-party.

## Validation & capabilities

### Manifest validator  —  _decided_

**Question:** How are manifests structurally validated?

**Choice:** ajv (JSON Schema)

**Rationale:** configSchema is itself JSON Schema; ajv validates both layers.

Options considered:
- **ajv (JSON Schema)** ✅ — Add ajv as a plugins-module dep; validate manifest + configSchema. Do not pull into gateway core.
- **joi** — Already a platform dependency; less natural for validating user-supplied JSON Schema config.
- **hand-rolled checks** — No new dep; more code, weaker guarantees.

### Capability vocabulary  —  _decided_

**Question:** How is what a plugin may touch constrained?

**Choice:** closed capability registry

**Rationale:** Grants must be a subset of a known, auditable vocabulary.

Options considered:
- **closed capability registry** ✅ — capabilities drawn from services/plugins/src/capabilities.js; unknown capability ⇒ reject. The core trust control.
- **free-form capability strings** — Flexible but unbounded; no way to reason about what a manifest can do.

### Webhook URL policy  —  _decided_

**Question:** How are webhook endpoints constrained (SSRF)?

**Choice:** https + private-range blocklist

**Rationale:** Security review already flagged atproto SSRF; same control applies.

Options considered:
- **https + private-range blocklist** ✅ — Enforce https in prod (mirror assertSecureCaUrl); block loopback/private targets unless allowlisted. Ties to SPRINT SP-11.
- **explicit allowlist only** — Only pre-approved hosts. Safest, least flexible.
- **no restriction** — Unsafe — rejected; left here to record the trade-off.

## Org / group / user ownership

### Scopes enforced in MVP  —  _decided_

**Question:** Which ownership scopes are fully enforceable in MVP?

**Choice:** platform + user (full)

**Rationale:** Org needs an admin authority concept; group needs per-module group-aware data first.

Options considered:
- **platform + user (full)** ✅ — platform (admin) and user (self) fully enforced; org partial; group declarable-not-enforceable.
- **+ organization** — Also enforce org scope — blocked by the missing org-admin RBAC concept.
- **all four including group** — Blocked: no domain module carries group_id, so group scope cannot be enforced on content.

**Choice:** _undecided_

- **build org RBAC now** — Add an organization + org-role model to auth. Correct long-term, large scope, off the MVP path.
- **defer org scope entirely** — Ship platform + user only; add org scope later.

**Choice:** _undecided_

## Token / CA / Auth

### Inbound plugin auth (MVP)  —  _decided_

**Question:** How do plugin callbacks authenticate to the platform?

**Choice:** derived service token

**Rationale:** Reuses existing service-token machinery; CA path needs a cert decision.

Options considered:
- **derived service token** ✅ — X-Service-ID: plugin:<key> + HMAC via serviceToken.js; authenticatePlugin() loads the install. Simplest for MVP.
- **CA-issued scoped token** — CA /api/tokens/generate with narrowed permissions. Real expiry/revocation, but needs a certificate.
- **derived now, CA in Phase 2** — Ship derived tokens for MVP; migrate to CA tokens once cert issuance is decided.

### Outbound webhook signing  —  _decided_

**Question:** How are outbound webhook deliveries signed?

**Choice:** HMAC (plugin:<key>)

**Rationale:** Consistent with existing service-to-service HMAC identity.

Options considered:
- **HMAC (plugin:<key>)** ✅ — X-Plugin-Signature = HMAC-SHA256(body, deriveServiceToken("plugin:"+key)). Symmetric, simple, matches platform.
- **mutual TLS** — Stronger, heavier ops; revisit if plugins become a public marketplace.

### Plugin CA certificate (Phase 2)  —  _open_

**Question:** When CA tokens arrive, what certificate backs a plugin?

**Choice:** _undecided_

Options considered:
- **synthetic "plugin" cert** ⭐ — One platform-owned cert namespaces all plugin tokens. Simple, central revocation.
- **real per-plugin cert** — Each plugin gets its own cert/identity. Strongest isolation, most lifecycle overhead.
- **stay on derived tokens** — Never issue CA tokens to plugins; keep HMAC service tokens only.

## Lowcode ↔ Plugin relationship

### How lowcode relates to plugins  —  _open_

**Question:** Is the low-code platform the authoring layer for plugins, or a parallel platform sharing infra?

**Choice:** _undecided_

**Rationale:** Open by design (you chose "explore both"). lowcode-platform.spec.json + scripts/lowcode-tui.js are the parallel-track artifacts.

Options considered:
- **A · Lowcode authors plugins** — The low-code studio IS the visual front door that emits declarative-kind plugin manifests.
  - 👍 One runtime: lowcode flows execute on the same hook bus + moderator engines
  - 👍 No second execution/permission/token model to build or secure
  - 👍 A low-code app inherits plugin scoping (platform/org/user) for free
  - 👍 Smaller surface area — fits release-engineering-first posture
  - 👎 Lowcode is constrained to what the plugin manifest can express
  - 👎 Rich app-builder features (custom entities/forms) may not map to a "plugin"
  - 👎 Couples two roadmaps — plugin manifest changes ripple into the studio
- **B · Separate, shares infra** — Lowcode is its own platform (entities/forms/flows) reusing the plugins module's scope model, capabilities and CA/auth.
  - 👍 Lowcode can grow its own data model (entities/forms) beyond plugin manifests
  - 👍 lowcode-platform.spec.json already models entities/actions/triggers/roles/forms
  - 👍 Each roadmap evolves independently
  - 👍 Plugins stay a thin extension mechanism; lowcode a full app builder
  - 👎 Two runtimes/execution engines to build, secure and operate
  - 👎 Risk of divergent permission/token models — more to audit
  - 👎 Duplicated scope-resolution and dispatch logic unless carefully shared

### Expanded scope delivered (beyond the original plan)
Per the follow-up request, these were implemented now rather than deferred:
- **Lifecycle + state-machine management** — generic FSM engine; install lifecycle with guarded, audited transitions (`plugin_transitions`); low-code record state machines.
- **Strong-typed properties + enums + lookups** — typed entity fields with dimension/measure roles + aggregation (Tableau/PowerBI-style) and reusable lookup lists (`LcLookup`).
- **Real webhooks** — HMAC-signed outbound delivery with retry + circuit breaker, inbound signature verification, and managed endpoints (`PluginEndpoint`, `/api/endpoints`).
- **Sandboxed native JS** (`script` kind) — worker-thread + `node:vm` isolation; the only capability is a host-brokered `platform.*` API whose I/O is signed and routed through the token/CA gateway. Gated by `PLUGINS_SCRIPT_ENABLED`.
- **Endpoint management** — CRUD over named inbound/outbound endpoints with SSRF guards.

A new added kind `script` joins `declarative` / `webhook`; `internal` remains post-MVP.
