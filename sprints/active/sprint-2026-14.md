### Sprint-scope notes per ticket

- **FEAT-090 (sr warm-up, M).** C/B: **APPROVE (build now)** — assessed as the
  best value-per-point in the whole slate (~135-LOC standalone reference, no
  schema, no infra). Two things to respect. (1) The **gateway's
  `compression()` middleware buffers SSE** — this is the one real gotcha named
  in the assessment; if streaming appears to work but tokens arrive in one
  burst, that is where to look, not in the backend. (2) The
  `src/modules/registry.js` `socketNs` change is **structural and needs
  systems-architect sign-off** — scheduled day 1–2 below. Non-streaming
  requests must behave exactly as today, and unauthenticated socket connects to
  `/cortex` must be rejected by CA token auth middleware like every other
  namespace. Update `API_SURFACE.md`. Gates FEAT-091 next cycle.
- **FEAT-081 (anchor, M–L).** C/B: **APPROVE-REDUCED** — ship the **sequential**
  engine with 8 step types (prompt · skill · retrieve · guardrail · moderate ·
  transform · condition · tool_loop) and `{{var}}` interpolation. **The 9th type,
  `parallel`, is deferred to FEAT-096** — the single-resident-model semaphore
  serializes parallel LLM steps anyway while `parallel` carries most of the
  engine's failure-mode complexity. **Critical spec-compat requirement: the spec
  format must accept and validate `parallel` from day one and reject it only at
  *enable* time with a clear "not yet supported" error** — this is why FEAT-080's
  spec shape got an architect glance last cycle, and it is what stops every
  agent definition needing a rewrite when FEAT-096 lands. Two more invariants:
  guardrails are added per-step and **never bypassed**, and the `retrieve` step
  **degrades gracefully to an empty result, not an error**, until FEAT-095 lands.
  Per-step inputs/outputs must land in the FEAT-080 run transcript.
- **BUG-066 (jr, S).** Strip the internal `__createdAtUs` alias from the
  message-history bodies (`GET /cortex/api/v1/chat/:id`,
  `GET /cortex/api/v1/cs/chat/:id`). The session-list handlers already project
  explicitly and are clean — copy that pattern. Cosmetic, but do it before
  anything documents or depends on the shape.
- **BUG-064 (jr with a dba glance, S).** Dev-boot `sync({ alter: true })`
  accretes duplicate constraints on every gateway start — the live DB currently
  carries `chat_messages_session_id_fkey1..10` and tripled `agent_runs` FKs.
  Same defect family as BUG-062. Two halves: stop the accretion, and clean up
  what has already accumulated. The cleanup half is a live-DB `ALTER`, so it
  **routes past the dba** and cannot go through sync `db:migrate` — run the
  migration's `up()` directly. `npm run db:check` must still exit 0 after.
- **BUG-065 (jr, S).** `.unref()` or fake-timer the pre-existing 5s `setTimeout`
  in cortex `tests/unit/client.test.js`, matching the BUG-055/BUG-061 teardown
  posture. The timeline suite prints the same warning class — sweep it in the
  same pass **if the cause matches**; do not force an unrelated fix into scope.
- **BUG-067 (dba-owned, S).** BUG-063's fix is correct but orders on
  `to_char(created_at ...)`, which is opaque to the planner — `EXPLAIN` shows a
  `Sort` node, so `chat_messages_session_id_created_at` cannot serve the
  ordering and every page sorts the whole match set. dba picks the fix:
  **matching expression indexes** (code unchanged) or **keep the plain column in
  `ORDER BY` and cast only the cursor side** (no new indexes). Whichever is
  chosen, **BUG-063's guarantee that the seek and the sort use the identical key
  must survive** — that equivalence is the entire fix, and QA's same-millisecond
  walk is the regression test. Re-run it before calling this done.
- **TASK-068 (qa, S, P2 — the one to prioritize).** FEAT-070's block enforcement
  was smoke-verified over REST only; the socket namespace is a second
  independent send path and the one the SPA actually uses for live sends. If
  enforcement is missing or partial there, that is a **block bypass**, not a
  test gap — file a `BUG` at P1/P2 per impact and do **not** fix it under this
  ticket. Raised P3 → P2 at filing for exactly this reason.
- **TASK-069 / TASK-070 (qa, S each).** The cheap two. TASK-069's env-limited
  skip has outlived its reason (infra has been up for cycles) — a red result is
  an acceptable, informative outcome given the known auth backlog. TASK-070
  should land **before** any RAG-track work starts writing embeddings into the
  dev DB.

## Risks

- **Two features in one sr track.** Accepted knowingly by the owner steer. The
  mitigation is ordering, not scope: FEAT-090 is genuinely bounded (no schema,
  no infra, a known reference implementation) and runs first, so if anything
  slips it is FEAT-081's tail — and FEAT-081 has a natural cut line, since the
  8 step types can land incrementally with `condition` and `tool_loop` last.
  **If the sprint runs long, cut step types — never the `parallel`
  accept-but-reject-at-enable behavior**, which is what protects every future
  agent definition.
- **FEAT-081's edge cases are the largest test-cost item in the whole slate**
  (its own C/B says so): condition-on-missing-var, guardrail-halt, step timeout.
  The CI test job is non-blocking, so QA's manual pass is the real gate — and
  QA is also carrying three TASK tickets this cycle. If squeezed, QA
  prioritizes FEAT-081 verification and TASK-068 over TASK-069/070.
- **SSE through the gateway.** `compression()` buffering is a known trap that
  makes streaming look broken in a way that points at the wrong layer. Called
  out in the scope note so nobody rediscovers it the slow way.
- **BUG-067 could silently undo BUG-063.** The whole correctness argument rests
  on the seek predicate and the sort using the *identical* key expression. Any
  fix that changes one side must change the other. QA's same-millisecond walk
  is the regression test and must be re-run — this is written into the ticket.
- **Deferred gates are now on their second and third roll.** FEAT-078's ADR
  sign-off has been "slated for next grooming" twice. It is not scheduled again
  here (the sr track is full), but it blocks FEAT-078 → FEAT-079 → part of
  FEAT-093's path, and the cost of the gate itself is small. If it rolls a third
  time, it should be escalated as a decision rather than a scheduling problem.
