Exprsn Platform — Service Documentation

The Exprsn Platform consolidates ten formerly standalone microservices into a single Node.js process behind one HTTPS port (default 8443). Each former service is now a module: an Express app mounted at a path prefix on a unified gateway (src/gateway.js), with its tables isolated in its own Postgres schema and its real-time events attached as namespaces on one shared Socket.IO server. The canonical module list lives in src/modules/registry.js.

This documentation set covers four of the platform's modules. Each page describes the module's purpose, full endpoint inventory (with gateway-prefixed paths), data models, configuration, real-time events, background jobs, and integration points.

Documented services

Exprsn-CA

/ca · schema: ca · socket: /ca

The certificate authority and token authority. X.509 issuance (root → intermediate → entity), OCSP responder, CRL distribution, the CA Token Specification v1.0 used by every other module for auth, hash-chained audit logging, and RBAC.

Exprsn-Auth

/auth · schema: auth

Centralized identity: registration, login, MFA (TOTP + backup codes), sessions, password lifecycle, social OAuth, a full OAuth2/OIDC provider (PKCE, discovery, JWKS), SAML 2.0 SSO, LDAP/AD sync, and multi-tenant RBAC.

Exprsn-Timeline

/timeline · schema: timeline · socket: /timeline · worker

The social feed: posts, likes/comments/reposts/bookmarks/follows, ranked home feeds, lists, trending, search (ElasticSearch), attachments via FileVault, Bluesky federation, and Bull-queue fan-out processed by a separate worker.

Exprsn-Prefetch

/prefetch · schema: prefetch · worker

Read acceleration for timelines: tiered hot/warm Redis caching, priority-queued prefetch jobs, activity-based scheduling, cache metrics, and Kubernetes-style health probes.

Database Model

database: exprsn · schemas: ca, auth, timeline, prefetch

The data layer across the documented services: schema-per-module isolation, every table with key columns and relationships, Redis runtime stores, and the logical UUID references that cross schema boundaries.

How the modules fit together

InteractionDescription
CA → everyoneAll modules authenticate requests with CA tokens; validation happens against /ca/api/tokens/validate or via in-process IPC (token:validate, cert:validate).
Auth ↔ CAAuth delegates CA-token generation/validation to the CA and monitors it at /auth/health/ca.
Timeline → PrefetchPrefetch pulls user timelines from Timeline (GET /api/timeline/user/:userId) and serves them from hot/warm Redis tiers.
Timeline → Herald / Spark / FileVault / BlueskyNotifications, real-time broadcasts, attachment storage, and AT-Protocol federation respectively.
Service-to-service authHMAC tokens derived from SERVICE_TOKEN_SECRET (headers X-Service-ID + X-Service-Token); the unified process presents SERVICE_ID=platform. Inter-module HTTP still flows through *_SERVICE_URL vars, which point back at https://localhost:8443/<module>.
