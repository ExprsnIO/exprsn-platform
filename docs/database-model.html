Database Model

Database
One PostgreSQL database: exprsn
Isolation
One schema per module (Sequelize define.schema), one for each of the 14 modules in src/modules/registry.js: ca, auth, spark, nexus, filevault, vault, timeline, prefetch, moderator, live, atproto, plugins, lowcode, cortex
Keys
UUID primary keys throughout (a few tables use a natural string PK — e.g. *_config.section, ca.acme_nonces.nonce, atproto.labels.seq); Sequelize-managed createdAt/updatedAt timestamps. Several tables use epoch-ms BIGINT instants rather than DATE
Migrations
Default path db:migrate (scripts/migrate-sync.js) syncs each module's models into its schema; db:migrate:raw (scripts/migrate-modules.js) replays historical migration files with DB_SCHEMA/DB_NAME injected via env. Audit drift with db:check

Modeling principles

Each module owns its schema and never declares foreign keys into another module's schema. Cross-module references (a Timeline post's userId, a Prefetch job's user_id) are logical UUID references resolved through service APIs or IPC, not database constraints. Within a schema, conventional Sequelize associations and FK constraints apply. Several modules use soft deletes (a deleted flag) instead of row removal, and the CA's audit log is append-only with a hash chain.

Known gap (STATUS.md #1): raw migrations with unqualified table names can land in public instead of the module schema. Schema-qualify table names or set a searchPath when touching migrations.

The diagram highlights four representative core schemas. The platform has one schema per module for all 14 modules; every schema is documented in full below. See the platform model for the module-topology and dependency diagrams.

Schema: lowcode

Tables backing the Low-code runtime (flag LOWCODE_ENABLED). It reuses the plugins module's trust layer (scope model, capability vocabulary, condition evaluator, state-machine engine, hook bus) at the service level; its tables are independent of the plugins schema.

Dynamic entities without dynamic tables: low-code does not create a physical table per user-defined entity. Each entity's typed field schema lives in lc_entities.fields (JSONB); every user record of every entity is stored generically as a row in the single lc_records table with values in lc_records.data (JSONB). Optional per-entity storage selects where records physically live (db default, mirror, filevault, or export).
