Overview

Exprsn-CA is the platform's X.509 public-key infrastructure and token authority. It issues and manages the full certificate hierarchy (root, intermediate, entity, SAN, code-signing, client, and server certificates), operates an OCSP responder (RFC 6960) and CRL distribution point (RFC 5280 §5), and implements the Exprsn CA Token Specification v1.0 — signed, permission-scoped tokens that every other platform module uses to authenticate API requests.

It also maintains its own user/group/role model with RBAC, a cryptographically chained audit log (each entry's hash includes the previous entry's hash, making tampering evident), and real-time certificate/token status events over Socket.IO. ACME v2 (RFC 8555) data models and migrations are present, but the protocol handlers are not yet implemented.

As a platform module it exports { name, app, registerSockets(io), init(ctx) } — no listen(), no views. init() connects IPC, Redis, Postgres, and the storage layer, auto-generates a root CA certificate if none exists, and starts the CRL service.

Issued certificates carry standard X.509 v3 extensions: cRLDistributionPoints (pointing at /crl/current.crl), authorityInfoAccess (OCSP + caIssuers), basicConstraints, keyUsage, extendedKeyUsage, subjectKeyIdentifier, and authorityKeyIdentifier. X.509 construction uses node-forge; hashing and HMAC use the native crypto module. Tokens are signed with RSA-SHA256-PSS.

Revocation

CRL: regenerated every CRL_UPDATE_INTERVAL seconds (default 3600), nextUpdate = thisUpdate + CRL_NEXT_UPDATE_DAYS (default 7), with an atomic monotonic cRLNumber from CrlCounter. OCSP: signed DER BasicOCSPResponse with in-memory response caching (default 300 s TTL; revoked-status responses capped at 60 s), issuer-cert hash caching, and batch checking.

Storage backends

Pluggable certificate/private-key storage (services/ca/storage/): disk (PEM files), S3, or PostgreSQL (BYTEA), selected via STORAGE_TYPE. Private keys are wrapped with AES-256-GCM (storage/keyEncryption.js).

Socket.IO events — namespace /ca

DirectionEventPayload / behavior
Client → servercertificate:subscribe{ certificateId } — join room certificate:{id}
Client → servertoken:subscribe{ tokenId } — join room token:{id}
Server → clientcertificate:updatedCertificate object, broadcast to its room on status change
Server → clienttoken:revoked / token:expiredToken ID (+ reason), broadcast to the token's room
Server → clientaudit:loggedAudit entry, broadcast to user:{userId}

Connections auto-join their user:{userId} room. Session middleware applies; unauthenticated sockets are allowed but flagged socket.authenticated = false and checked by handlers.

Authentication & middleware

MiddlewareBehavior
requireSession401 JSON error without a session user
requireAdminSessionRequires roles admin, super-admin, or ca-admin (401/403)
requireSessionOrServiceAccepts a session or HMAC service auth via X-Service-ID + X-Service-Token (HMAC-SHA256 over the service ID with SERVICE_TOKEN_SECRET; verified by shared/utils/serviceToken.js)
requirePermissions(...)Resolves the user's roles/groups and checks every listed permission
optionalAuth, attachUserToLocalsNon-blocking user attachment

CA token validation (tokenService.validateToken) checks status, verifies the RSA-PSS signature, matches permissions and resource, decrements use counts for use-based tokens, and caches valid results in Redis (300 s TTL). Rate limits: standard 100 req/15 min; strict 10 req/15 min (e.g. password verification).

Integration & key files

IPC: the CA registers handlers for cross-module validation — cert:validate (responds with validity, status, dates) and token:validate (validity, status, expiry, permissions). Other modules (Timeline, Prefetch, Auth) call the CA's /api/tokens/validate endpoint or these IPC events to authenticate requests.

Init order: IPC worker → config validation → Redis → Postgres → storage layer → root CA auto-generation → CRL service.
